# Web画面を実測する

[実装方針の適用境界](../deliver/implementation-scope.md)を適用してから進める。

入力は元の要求、DESIGN.mdの適用節、変更前の画面、実装差分、代表データと起動方法。
実装を推測して合格にせず、対象repoのbuild/起動/E2E設定を使う。

1. 自動E2EはChromium + Playwrightで実行する。Obscuraはアサーション駆動E2Eの代わりにしない。
2. 同じデータとviewportで変更前後の全体を表示し、画像と実際の操作を確認する。
   主情報の面積、見える件数、重複、アクセントの強さを今回の条件へ対応付ける。
   同じ実用的な状態で、主情報から選択し、必要時に詳細を開き、目的へ到達するまでを比較する。
   読む量と入力・選択・確認の回数、失敗原因から修正先を開いて復帰する手間を観測する。
   画像の保存、部品寸法、エラー文字列の存在だけで使いやすさを合格にしない。
3. 新規UIは明暗・狭幅・長文・空/失敗・主操作とkeyboard/focusを実際に通す。
   部分変更は影響する条件だけを選ぶ。テーマ変更なら両テーマ、配置変更なら代表件数と文字拡大を扱う。
   CSS値を読めただけで外観を確認済みとしない。
4. 失敗があれば実装担当へ再現条件を返して修正する。必要な挙動の回帰テストは対象repoへ残し、
   散文やライブラリそのものを再テストしない。

出力は要求/製品設計の条件ごとの観測値・画像・操作結果、失敗と未確認。
[ui-review](../ui-review/SKILL.md)へ渡す。自分のプロセスと隔離データだけを片付ける。
画面が開かない場合は必要な起動修正まで進め、依頼範囲内の未達を単なる提案にしない。
