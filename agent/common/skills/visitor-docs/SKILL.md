# 訪問者のための文書を作る

読者、読む目的、公開範囲を定め、実装と公開される資料から内容を確かめる。
既存の言語と文体を尊重し、訪問者が製品の目的から導入・基本操作へ進める順序にする。
データ集や開発用テンプレートなら、その読者が必要とする取得・使用手順を扱う。
必要な制約、互換性、ライセンス、データの保護に関する説明を短さのために落とさない。

個人の作業指示、会話、完了報告、タスク固有の検証記録はtask-serverへ置く。
再利用する開発・運用手順は公開の詳細文書へ分け、READMEから必要な箇所へ案内する。
読者がアクセスできない資料を、導入に必須の説明の代わりにしない。
作業の完了を製品の特徴として書かず、現在の挙動・条件を根拠に記す。

## Jevによる項目別の確認

導入済みの公式 `typesafe-ai` を読み、現行のScore APIを確認する。
認証情報は [change-reviewの問い合わせ手順](../change-review/SKILL.md#jevへの問い合わせ) を使う。
新たな認証設定や共通レビュー基盤は作らない。このskillのスクリプトは文書評価だけを担う。

対象文書ごとに、repo外へ `context.json` を用意する。必須項目は以下の4つの文字列。

- `reader`: 初めて読む人とその前提知識。
- `purpose`: 読み終えた人が実行できるべきこと。
- `exposure`: 公開・内部向けなど、読者が参照できる範囲。
- `evidence`: 実装、配布物、リンク先の関連本文、確認したコマンドと結果。

根拠は実際の本文を含める。パスや自己評価だけで代用せず、秘密値は送信前に除く。
参照資料を取得できない場合は未確認とする。翻訳版や下位READMEも文書ごとに評価する。

`<skill-dir>` はこのSKILL.mdのあるディレクトリ。Python 3の標準ライブラリだけを使う。
`<evidence-dir>` は新しい出力先とし、前回の証拠を上書きしない。

```sh
python3 <skill-dir>/scripts/evaluate.py --context /tmp/context.json \
  --output <evidence-dir> README.md
meiseki-lint README.md > <evidence-dir>/lint.json
```

[採点基準](scripts/questions.json) は客観性、読者適合、初回利用、構成、簡潔さの5項目。
各項目は0〜3のScoreで、3はその観点に修正事項がない状態。Noulの確率とは区別する。
`request.json` に対象全文と問い、`response.json` に応答、`summary.json` に項目別の値を保存する。
Jevは理由の文章を生成しない。担当が低い点や不確かな項目から原文と根拠を照合する。

終了コード0は採点取得、1は重点確認、2は入力・API・応答の未確認を示す。
既存出力先などの起動エラーも未確認。いずれも文書の完了宣言ではない。
Scoreが2.5未満かconfidenceが0.5未満なら重点確認へ回す。これは確認順の目安であり、
品質を保証する閾値ではない。平均・合計による欠点の相殺はしない。

## 完了条件

- 全5項目の有効な採点を受け取り、各観点で実際に見つかった問題を解消した。
  高得点でも既知の欠陥を残さず、低得点を誤判定とするなら原文の根拠と判断を記録する。
- 修正した本文を使って影響する項目を再確認した。点数を上げるだけの反復はしない。
  API失敗、入力不足、項目欠落、根拠との不一致が未解決なら完了にしない。
- meiseki-lintを実行した。終了0は指摘なし、1は指摘あり、2以上は実行エラー。
  指摘は修正するか誤検知の理由を残し、実行エラーを指摘なしとは扱わない。
- コマンド例・参照先・翻訳間の整合を確認し、既存の形式検査も通した。
  Markdownの字面を固定するテストは作らない。

本文の版、モデル名、各Scoreとconfidence、担当の根拠、修正、lint結果を作業証拠に残す。
採点結果をREADMEへ追記しない。commit・pushは依頼範囲と [git](../git/SKILL.md) に従う。
