# spike

目的は、ユーザーが確かめられる体験を最短で作ること。
将来の拡張や網羅的な堅牢化は、本題に必要になってから行う。
version の大小で適用を決めず、既存プロジェクトの新しい体験にも使える。

[共通契約](../deliver/CONTRACT.md) と [工程・所有者](../deliver/PROCESS.md)
に従う。分担・検証・レビュー・commit・停止の規則をここで重複定義しない。

## 進め方

1. **狙う体験を絞る**: 依頼から、何が動けば試せるかを短い達成条件にする。
   数を揃えるために要件を落とさない。knowledge は index から関連事項と
   テスト戦略だけを読む。新規の土台は既存 template が適合すれば利用する。
   既存 repo の土台比較や全面移行を毎回の必須作業にしない。
   frontend の変更が必要なら、実装前に `frontend-design` を読み、
   project の design authority と interaction contract を達成条件へ反映する。
2. **検証方法を決める**: 既存のテスト戦略に従い、未定なら実行可能コードの
   挙動と副作用の隔離方法を決める。再利用する新しい戦略は knowledge に残す。
   独立 planning が役立つかは共通契約に従って判断する。
3. **動くものを作る**: 実行可能コードはできる限り red → green で作る。
   TDD に適さない探索や環境依存の部分は、理由と代わりの検証を明示する。
   Markdown の字面を検査するだけのテストは作らない。
4. **体験を確かめる**: 必要なテスト・build・lint に加え、実際の起動や操作で
   主要な体験が成立することを確認する。frontend を変更する場合は
   対象 flow を Chromium + Playwright で確認する。
   未解決の重要な視覚・操作判断があるときは designer / ui-checker を使う。
5. **レビュー・修正・commit・報告**: 共通契約に従う。動いた体験と証拠、
   残した制約を短く報告する。動作に必要な不具合を「試作だから」で残さない。

ライセンスや公開方法はプロジェクトと依頼に従う。MIT や v0.1.0 を一律に強制せず、
既存 version をこの skill の都合で変更しない。release 準備が依頼に含まれる
場合だけ、その準備と未解決事項も確認する。
