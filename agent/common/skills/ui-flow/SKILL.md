# 操作の前後を設計する

[実装方針の適用境界](../deliver/implementation-scope.md)を適用してから進める。

入力は元の要求、既存画面と呼出し経路、[design-context](../design-context/SKILL.md)で特定したデザイン方針と不足。
未解決なら先にdesign-contextを読む。配色や部品寸法はここで所有しない。

1. 利用者が何をしている最中に、何を1回操作し、どの結果へ戻るかを具体化する。
   主操作を一つ定め、初回準備と普段の操作を分ける。設定頻度と実行頻度を混同しない。
   保存済み条件や確定した初期値で省ける入力・選択を見つけ、通常経路で毎回要求しない。
2. 通常起動、外部リンク・NFC・通知など今回の入口から、成功・失敗・再試行・取消し・戻るを追う。
   許可を求める場所、同じ操作の反復、実行中の競合も影響する範囲で決める。
   他アプリの閲覧・再生・入力を遮るか、権限や確認画面が唐突に出るかを含める。
   失敗時は原因、直す項目と到達先、修正後の再試行・復帰を具体化する。一般的な失敗文だけで終えない。
3. 状態は必要なタイミングで利用者へ伝える。通知の要否は元の要求と実際の結果で決め、
   API受付を成功へ読み替えない。状態不変の反復で情報を増やす必要があるかを判断する。

出力は製品DESIGN.mdへ反映する代表経路、主操作、必要な状態と復帰、維持する既存操作。
実装担当が次の画面と判定条件を判断できれば終了する。未指定の可逆な選択は担当が決める。
実装は [frontend-design](../frontend-design/SKILL.md) または [android-ui](../android-ui/SKILL.md)へ渡す。
画像だけで操作設計済みとせず、後段の環境別実測で代表経路を実際に通す。
