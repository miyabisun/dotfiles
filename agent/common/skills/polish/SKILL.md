# polish

目的は、既存の体験を壊さず、ユーザーの不満を解消すること。
version を問わず使い、改善の規模で儀式や担当数を増やさない。

[共通契約](../deliver/CONTRACT.md) と [工程・所有者](../deliver/PROCESS.md)
に従う。分担・検証・レビュー・commit・停止の規則をここで重複定義しない。

## 進め方

1. **不満と現在地を確認する**: knowledge の index から関連事項と既存の
   テスト戦略を読む。不具合なら可能な範囲で再現し、望む挙動と守る既存挙動を
   達成条件にする。独立 planning が役立つかは共通契約に従って判断する。
   frontend の変更が必要なら、実装前に `frontend-design` を読み、
   project の design authority と interaction contract を達成条件へ反映する。
2. **変更範囲を決める**: 既存の未コミット変更を把握して保護する。
   無関係な dirty file があるだけで停止しない。安全に分離できなければ
   別の作業場所を用意するか、必要な調整を行う。
   既存の整形差分は今回必要な範囲に限定する。広い基線正規化は必須にしない。
3. **直す**: 要件を満たす最小の修正を選ぶ。必要なら関数分割や設計変更も行う。
   規模が増えたという理由だけで差し戻さず、目的・互換性・権限が変わる場合は
   その判断を確認する。
4. **回帰を確かめる**: 実行可能コードの不具合はできる限り失敗するテストを
   先に作り、修正で通ることを確かめる。既存テストで十分なら重複を増やさない。
   変更に必要な既存 checks を実行し、困難な検証は理由と代替の証拠を残す。
   frontend を変更する場合は、影響する state・viewport・
   input を Chromium + Playwright で確認する。視覚・操作上の不満には必要に応じて
   ui-checker の独立した実測を使う。
5. **レビュー・修正・commit・報告**: 共通契約に従う。修正後に必要な checks を
   再実行し、未解消の blocking を完了扱いしない。何が改善したか、検証結果、
   残る制約を短く報告する。

Markdown だけの変更は、意味・参照・指示の整合を確認する。形式 validator が
あれば実行するが、文字列の存在を確かめる回帰テストは作らない。
