# Jevの項目別レビュー

実装後の確認として [deliver](../deliver/SKILL.md) が呼び出す。タスク登録前の候補は [task-creator](../task-creator/SKILL.md) の担当が自分で確認し、ここへは渡さない。

実装レビューでは、主担当が[実装方針の適用境界](../deliver/implementation-scope.md)に従って実差分を確認する。
UI差分は [ui-review](../ui-review/SKILL.md) の結果と適用するデザイン方針の関連本文を含める。
実差分と検証結果を使う。同じ範囲の評価を重ねない。

通常はJevへ、適用する観点をまとめて問い合わせる。各値を0〜1の小数のまま扱い、真偽へ丸めない。
Jevを使えない時は [Jevを使えない時](#jevを使えない時) の代わりの手順に従う。

## 入力と対象選択

元のユーザー発言・明示制約と、判断対象をテキストで渡す。
実差分・必要な周辺コード・検証結果を添える。
Jevの `state` に必要な本文を含める。ローカルpathだけを渡して読めたことにしない。
合意済みの仕様変更、認証・API・永続データへの影響も入力へ含める。
UIではDESIGN.mdと変更前後の画面の確認結果を添える。
秘密の値は送信前に伏せ、判断に必要な位置・用途・周辺構造を残す。

`description_matches` と `unrequested_restriction` は毎回確認し、他は差分・利用経路から適用対象を選ぶ。
適用外は担当が理由付きで `N/A` と記す。判断に必要な資料の不足は未確認とし、0点や適用外にしない。

## チェックリスト

各行の問いを独立に評価する。対象は今回の変更によって生じる問題である。
`description_matches` だけは高いほど適合し、残りは高いほど問題がある可能性を示す。

| 項目 | 問い（1に近いほど「はい」） |
| --- | --- |
| `hardcoded_secret` | 実際の認証情報をソース・配布設定・ログへ直書き、または露出させる変更か？ ダミー値・環境変数名・意図された秘密の保管先は除く。 |
| `injection_risk` | 信頼できない入力が適切な分離・処理なしに解釈され、SQL・コマンド・HTMLなどへの注入を可能にする変更か？ |
| `auth_regression` | 必要な認証・認可を回避できる、または正当な利用者を誤って拒否する変更か？ 合意されたアクセス方針を基準にする。 |
| `adds_tautology_tests` | 常に真となる比較や実装の言い換えだけで、期待する挙動の誤りを検出しないテストを追加しているか？ |
| `breaks_api` | 合意されていないAPI・CLI・公開形式の変更により、既存の呼出し側との互換性を壊すか？ |
| `unsafe_data_migration` | スキーマ・永続データの変更で、合意外のデータ喪失・不整合・移行不能を起こすか？ |
| `description_matches` | 元の要求と明示制約を満たす変更であり、その説明が実際の内容と一致しているか？ |
| `unrequested_restriction` | 元の要求・製品・安全上の根拠がない制約や拒否条件で、対象製品の標準的な利用経路（周辺機器が無い構成での基本操作など）を塞ぐか？ 所持・構成の記述を必須条件へ変えた場合を含む。明示された要求・合意済みの制約は除く。 |
| `debug_leftovers` | 一時的なデバッグ出力・停止・試験用分岐が成果物へ残っているか？ 必要な運用ログは除く。 |

`touches_auth` と `data_migration` は対象を選ぶための変更情報とし、不具合を上の2項目で問う。
`docs_only` はファイルと内容から担当が判断する。文書・skillだけの変更も、適合性などの確認は省かない。
`merge_ready` は採点しない。合計・平均点で問題を相殺せず、完了判断は検証と項目別の確認に基づく。

## Jevへの問い合わせ

JevはTypeSafeのモデルで、渡した文章（`state`）について、各問いの答えを確率で返す。
[HTTP API](https://docs.typesafe.ai/api/system-one) の `POST https://api.typesafe.ai/v1/systemone` を、
`Authorization: Bearer <TYPESAFE_API_KEY>` を付けて呼ぶ。本文は次の形にする。

```json
{
  "model": "jev-latest",
  "state": "<元の要求・実差分・検証結果>",
  "questions": {"<項目名>": {"type": "noul", "instructions": "<本表の問い>"}}
}
```

`type: "noul"` は、問いの文が真である確率を0〜1で返す型である（[Noul](https://docs.typesafe.ai/primitives/noul)）。
ID自体はモデルへの指示にならないため、問いには意味と除外条件を含める。
選んだ項目を同じ `state` で一括評価する。各問は独立しており、他の回答を参照させない。
長さの上限などが要る時だけ公式文書を読む。公式の `typesafe-ai` skillは組み込み方の指針で、この呼び出しには要らない。

APIキーは環境変数 `TYPESAFE_API_KEY` から読む。dotfilesの[導入手順](https://github.com/miyabisun/dotfiles/blob/master/docs/utilities.md#typesafe-credentials)を
済ませたマシンでは `~/.config/typesafe/env`（mode600）にある。保管庫との同期は導入手順が持ち、通常の実行では `rbw` を呼ばない。
非対話実行では、APIを呼ぶのと同じshellで次を実行する。キーの値は表示・記録しない。

```sh
. "$HOME/.config/typesafe/env" && export TYPESAFE_API_KEY
```

`answers.<項目>.noul` を項目名とともに報告する。
各回答が `type: "noul"` で、値が有限の数値かつ0〜1であることを確認する。
欠落・不正値・API失敗は未確認として扱い、0点で埋めない。

## Jevを使えない時

次のどれかを実際に確かめた時だけ、Jevを使えないと判断する。

- キーが無い、または読めない。この時はAPIを呼ばない。
- 通信できない。通信を止めるsandboxでは、そのruntimeの設定で通信を許された実行方法があれば、それで1回呼ぶ。
- HTTPの失敗、または応答全体が上の形に合わない。

その時は同じ `state` と問いをサブエージェントか別セッションに渡し、各項目を0〜1で答えさせる。
どちらも使えなければ、担当が各項目を自分で評価する。別モデルへの切り替えは要らない。
失敗した段階と理由、代わりに評価した者を報告に書き、代わりの値をJevの応答として書かない。

## 値を受け取った後

0.5は肯定と否定が同程度に不確かという意味で、問題の重大度が半分という意味ではない。
重大度の段階評価用のScoreとは区別し、今回は各問題の該当確率として扱う。

主担当が高いリスク値・低い適合値・0.5付近の不確かな項目から、必要な根拠を照合する。
Jevは理由の文章を生成しないため、疑わしい箇所の特定と修正は担当が行う。
確定した不具合は数値にかかわらず直す。未校正の数値だけで自動合格・自動mergeを決めない。
不足資料は担当が補い、実際に不足する製品判断だけをユーザーへ返す。

修正した箇所を検証し、必要なら影響する項目だけを再評価する。
点数を上げ下げするための反復や、好みによる改善提案・テストの再実行はレビューへ求めない。
指摘の分類・ID管理・専用の再レビュー形式は不要である。
依頼・結果を保存する場合はrepo外の一時領域に置く。確認できなければ実際の障害と残件を報告する。
