# task-creater

タスク作成時の要件・方針判断を所有する。直接開発では登録せず同じ判断を使える。
実装・検証・実装後レビューは [deliver](../deliver/SKILL.md) が所有する。

## 候補を作る

元のユーザー発言・明示制約・既存の合意と授権を保持し、担当の提案と観測事実を区別する。
[knowledge-read](../knowledge-read/SKILL.md)、現在の実装、product情報、既存タスクを必要な範囲で確認する。
利用者・利用環境、公開後に取り込む先、配備や設定変更の要否、完了を観測する操作と環境を埋める。
既知の情報は聞き直さず、結果を変える不足だけ最低限質問する。依存しない調査と候補作成は進める。

候補本文には目的・要求と根拠、対象と方針、実行先で達成できる完了条件、必要な引き継ぎを書く。
元の発言は引用または読める参照を添え、要約だけを正本にしない。

## 利用先と分割

工程名で分けず、実行環境・対象repo・引き継ぐ成果の違いで必要なタスクだけ分ける。

- Neovimプラグインの実装・公開 → dotfilesへの導入とsandbox上の利用確認は、両方sandboxになり得る。
- サーバーの修正・回帰検証・公開(sandbox) → 必要な配備と実機確認(homeserver)は実行先を分ける。
- 通常リリースが既存の自動更新で足りる場合、配備タスクを無条件に作らない。

後続の `depends_on` を前提タスクへ向け、対象版/artifact・適用方法・確認操作・成功の観測点を渡す。
作成時に版が未確定なら前提タスクの完了報告から受け取ると書く。
開発は自身の環境で達成した条件でdoneにできるようにし、実機確認の未実施だけでblockedにしない。
後続が残る問題全体を解決済みとも報告しない。候補作成を本番操作の授権と混同しない。

## 登録前レビュー

1. 導入済み `ponytail:ponytail` と `ponytail:ponytail-review` の公式skillを読み、主担当がultraで
   必要性を問い、最小性を1回確認する。既存機能、不要な抽象化・依存・設定・テスト・分割・工程を点検する。
   明示要求や必要な入力検証・データ保全などは削らない。外部pluginの本文を複製しない。
   ponytail-reviewはコード差分用なので、ここではその過剰設計の観点を候補の仕様・予定変更へ適用する。
   未実装コードのレビュー済み表示や架空の差分・削減行数は出さず、指摘は候補の箇所と削る内容で示す。
2. [共通review実行手順](../deliver/REVIEW.md) の `planning` で別モデルへ渡す。
   元のユーザー発言と制約、候補本文、必要な一次資料・利用経路を渡し、目的とのずれ、漏れ、未合意の追加、
   方針・実行先・依存・達成条件の不整合を確認する。同一モデルの子で代用しない。
3. 指摘を元の依頼と証拠に照らして修正する。通常は1巡と必要な指摘確認で終え、証拠なく反復しない。
   候補・結果・修正と確認済みの方針を読める形で保存し、タスク本文から参照して実装担当へ渡す。
   別環境から読めない一時pathだけにせず、必要な判断と指摘の解消根拠は本文にも短く残す。
   レビュー不能なら候補と実際の障害をrepo外に保存し、未実施を合格や登録済みとしない。
   規則上の新しいユーザー承認工程は設けない。

## 登録と引き継ぎ

既存タスクと重複しないレビュー済み本文を、現在のtask-serverのMCP/API契約で登録する。
`product`・`execution_target`・`depends_on`・完了条件を登録結果で照合する。
MCPに必要な入力がない場合は公開APIを確認し、指定を黙って落とさない。
作成だけの依頼はdraft。ready化や実行の授権があれば従い、必要な後続もその範囲で登録する。
登録失敗は本文と未登録理由を残す。成功したID、状態、依存と残る作業を短く報告する。

状態変更だけにはこのレビューを繰り返さない。目的・範囲・達成条件の大幅な変更時は影響点を再確認する。
直接開発は候補を短い実装方針として、必要な事前判断と結果をdeliverへ渡すだけでよく、タスク登録は義務にしない。
既に同じ範囲を事前確認済みなら再利用し、実装はdeliverのPonytail fullへ戻す。
