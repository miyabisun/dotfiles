# delivery の共通契約

GLOBAL の自律性・授権・既存作業保護・テスト規則に従う。この文書は delivery 固有の差分だけを持つ。

## 方針・実装・検証

- 依頼と現状から達成条件を決め、[knowledge-read](../knowledge-read/SKILL.md) で関連判断・テスト戦略を読む。
  正本の適用する節を今回の構成・要件に照らし、実装方針に反映する。
- 作業の分担とレビュー方法は、変更の性質に応じて担当が選ぶ。
  サブエージェントは、並行作業・文脈の分離・別視点の検討などに役立つと判断したときに使える。
  委譲する場合は目的・担当範囲・達成条件と必要な情報を渡し、成果と証拠を確認して統合する。
- frontend の実装前には `frontend-design` で design authority と interaction contract を確認する。
  対象 flow は Chromium + Playwright で検証し、視覚・操作の達成条件と照合する。
- 変更に必要な test / build / formatter / linter をまとめて実行する。
  hooks の成功や無出力は検証済みの証拠ではない。修正後は影響する checks だけ再実行する。
  未実行・既存失敗・今回の回帰を区別し、必須検証の不足を完了扱いしない。

## レビュー

担当自身が依頼・達成条件・今回の累積差分・検証結果を照合する。
要件未達・回帰・検証の信頼性・不要な変更を調べ、具体的な影響と根拠のある指摘を扱う。
コード差分の複雑さは `ponytail:ponytail-review` を同じレビュー内で適用して確認する。
導入済み plugin の `SKILL.md` を一度読み、専用のサブエージェントや追加のレビュー工程は作らない。
未導入環境では [Ponytail の実装方針](PONYTAIL.md) で担当が確認する。
Ponytail の指摘は正しさのレビューを補う。必要な検証・入力検証・セキュリティを削減対象にしない。
修正後は影響する挙動を検証し、指摘を再確認する。未解消の要件未達や回帰を残して完了しない。
修正や新しい証拠なしに同じレビューを繰り返さない。指摘は新要件や承認権限ではない。
独立した視点が役立つと判断した場合は [独立レビューの実行](REVIEW.md) を利用できる。
依頼や project が独立レビューを明示的に要求している場合は、その要件に従う。

## commit・報告

検証とレビューを終えて、自分の差分を `git` skill で local commit する。変更不要なら空 commit は作らない。
未完了の checkpoint は作業 branch に保存できるが、完了・統合の証拠にはしない。
長い仕事は継続できる状態を file に残す。成果、検証、レビュー状態、残件を短く報告する。
外部レビューが所有する場合だけ [PROCESS.md](PROCESS.md) を読み、local レビューを二重実施しない。
