# deliver

新規開発と既存の改善を同じ手順で進める。`refactor` / `slim` は作業範囲を指定する入口であり、工程は増やさない。
GLOBAL の自律性・既存作業保護・テスト規則に従う。この skill は local commit までを授権する。
依頼済みの push・統合・release は対応 skill で続ける。

## 要件と設計

1. ユーザーの元の要件・明示制約・達成条件を把握し、実装方針を短く決める。
   [knowledge-read](../knowledge-read/SKILL.md) で関連判断と共有テスト戦略を読み、実装・利用経路と照合する。
   未記録のテスト戦略は開発着手時に決め、再利用する判断をknowledgeへ残す。
2. 設計・実装には導入済み `ponytail:ponytail` の `SKILL.md` を読み、fullを適用する。
   未導入なら公式pluginの導入経路を確認する。独自の要約で置き換えない。
   既読の指示は再利用する。設計段階の独立レビューは行わない。
3. frontend を実装する場合は [frontend-design](../frontend-design/SKILL.md) でProjectの設計を確認する。
   未解決の選択が成果を変える場合だけ [discuss](../discuss/SKILL.md) で比較し、担当が決める。

## TDDと検証

- 新規・変更する副作用のない処理はすべてTDDで実装する。
  期待する挙動のテストを書く → 意図した理由で失敗することを確認 → 最小実装で通す → 整理する。
  既存挙動を保つ整理では既存テストを使い、未検証の挙動だけ先にテストを補う。
- 副作用から判断・計算を分ける。隔離できる処理は一時directoryやstubで検証し、
  実際の起動・操作・外部への作用は必要な範囲で実行して確かめる。
  必要な入力検証・認可・データ保全・アクセシビリティは削らない。
- テストコマンドは対象repoの既存設定から選ぶ。共通のエージェントHookで未通過のコミットを止める。
  各repoへGit hookを配布しない。エージェント側の設定と共通コマンドはdotfilesが所有する。
  対象repoで `agent-test run -- <既存テストコマンドと引数>` を実行し、通過後にcommitする。
  stage・検証・commitは別コマンドで実行する。検証後に編集したら再検証する。
  中断報告が必要なら `agent-test pause` を実行する。これはcommitを許可しない。
  Markdownのみでも既存の形式lintなど、変更に適した実検証を記録する。空の成功コマンドで代用しない。
- 編集中の赤状態と中断報告は許す。テスト未通過でのコミット・完了扱いは許さない。
  必須検証を省略したりhookを迂回して成功扱いにしない。HookはTDDの実施順序までは証明しない。
- formatter / linter / build と、UIのChromium + Playwrightによる実操作を変更に応じて確認する。
  Markdownは内容・参照・形式を確認し、字面を固定するテストを作らない。

## 実装後のレビューと完了

主担当は `ponytail:ponytail-review` でコード差分を確認する。追加の担当や工程は作らない。
別モデルの [実装レビュー](REVIEW.md) は次の2点だけを扱う。

1. 元の要件とのずれがないか。
2. 実装方針が問題を解くか、その方針をコードが実現しているか。

指摘を修正し、影響範囲を検証して指摘の解消を再確認する。新しい証拠なしに同じレビューを繰り返さない。
外側が独立レビューを所有する場合だけ [PROCESS.md](PROCESS.md) に従い、二重に実施しない。

開発・検証・レビューで見つかった、依頼範囲外の具体的な問題や未決事項は、task-serverへdraft登録する。
完了報告前に主担当が既存タスクとの重複を確認し、該当productの新タスクとして登録する。
本文には観測事実・影響・未決の論点・元タスク（あれば）と証拠への参照を残す。
元の依頼の達成に必要な修正をdraftへ逃がさず、思いつきだけの改善案は登録しない。
実行先は作業が必要な環境に従い `execution_target: sandbox` / `homeserver` を明示する。
開発と実機作業を引き継ぐ場合の分割・depends_on・完了条件は
[task-workの引き継ぎ手順](../task-work/SKILL.md#開発と実機作業の引き継ぎ)に従う。
登録だけでready化や着手はしない。登録できない場合は本文をrepo外へ保存し、
未登録の理由と保存先を報告する。登録成功を確認したタスクのIDを完了報告に添える。

検証・レビュー・修正を終えて、自分の差分を `git` skillでlocal commitする。
成果、検証、レビュー状態、残件を短く報告する。完了には検証を通過したコミットが必要である。
変更不要なら空コミットは作らない。未完了なら作業と再開情報を保存し、完了とは報告しない。
