# slim

[共通契約](../deliver/CONTRACT.md) と [Ponytail の実装方針](../deliver/PONYTAIL.md) に従う。
外から見える挙動をすべて保つ整理は `refactor`。slimは不要な仕様や責務の削減まで扱う。

1. knowledge の関連判断と実装・利用経路・配備を読み、誰のどの用途に必要な機構かを確認する。
   コード内の参照がないだけで未使用と決めない。refactorから候補が来ていれば、その根拠と影響を確かめる。
2. 残す用途・挙動・データと、廃止する機能・設定・手順を達成条件にする。
   既存の依頼範囲で削減を進め、判断が必要なのは用途や影響が実際に未確定な部分だけとする。
   変更対象の古い規則や過去のagent判断を、削除できない理由にしない。
3. 対象の実装と、それだけを支える依存・設定・テスト・文書を一緒に整理する。
   廃止した仕様を既存テストのためだけに残さず、残す挙動と廃止後の動作を検証する。
   必要なデータ保全・移行・復旧は維持し、無関係なテスト失敗を削除で隠さない。
4. 共通契約のレビュー・指摘修正・commit を完遂する。
   廃止したもの、利用者への影響、減った設定・操作・保守負担と検証結果を報告する。

セキュリティやアクセス制御の削減では、knowledge-readでknowledgeの場所を解決する。
その `library/policies/security-by-exposure.md` を読み、現在の公開範囲と実際の経路に照らす。
外部へ集約する責務と、アプリが守る入力・認可・整合性を区別する。ポリシー本文は複製しない。
削減目標や専用の承認・監査工程は作らない。不要と判断できる対象がなければ、その根拠を報告する。
