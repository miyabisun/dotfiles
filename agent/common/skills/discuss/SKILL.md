# discuss

依頼に応じて案を広げ、価値・実現性・利用者への影響を比較して推奨を決める。
開発段階によるモード分岐や、独立した計画レビューは設けない。

1. 目的、既存の判断、実際に未解決な選択を確認する。
2. 設計案は `ponytail:ponytail` fullで必要性と最小の実現方法を考える。
   既存の利用習慣・互換性・操作数/認知負荷・復旧の容易さを比較する。
3. 有力案に実質的な差がある場合だけ選択肢を並べ、推奨と理由を示す。
   既存の依頼で判断できる実装方法は担当が決め、実際に不足する要件や権限だけを尋ねる。
4. 結論と次の一手を会話へ返す。検討だけの依頼ではrepoを編集しない。
   開発中なら判断を実装へ反映し、議論の終了を依頼全体の終了にしない。

既存の授権を探し、同じ承認を聞き直さない。議論そのものを必須の通過工程にしない。
将来の仮定やagentの判断を、現在のユーザー要求を阻む禁止規則にしない。
再利用する決定は、記録が必要なときだけ `knowledge-deposit` で外部knowledgeへ残す。
