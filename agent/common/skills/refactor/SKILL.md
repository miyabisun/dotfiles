# refactor

[共通契約](../deliver/CONTRACT.md) と [Ponytail の実装方針](../deliver/PONYTAIL.md) に従う。
不満や不具合の解消が主目的なら `polish`、新しい体験を作るなら `spike` を使う。

1. knowledge の関連判断・テスト戦略と実装を読み、処理経路・呼び出し元・副作用を追う。
   API・データ・エラー・時刻・順序・同時実行など、変更が触れる挙動を達成条件にする。
2. 既存の検証で変更前の状態を確認する。不足する挙動だけ実行可能な検証で補い、
   削除、既存機能への統合、標準機能での置換を優先して整理する。
3. 変更後に同じ挙動を確認し、共通契約のレビュー・指摘修正・commit を完遂する。
   減らせた責務や重複、検証結果、未確認の範囲を報告する。速度やメモリの改善は実測した範囲だけ述べる。

簡素化できる箇所が見つからなければ、その根拠を示して終える。削除行数の目標は作らない。
今回触る経路の不具合を見つけたら既存の依頼範囲で直し、意図した挙動変更として分けて検証・報告する。
Markdown は意味と参照の整合を確認し、字面を固定するテストは作らない。
